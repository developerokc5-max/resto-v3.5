Web App Executive Briefing · Store Monitoring System OK Chicken Rice Pte Ltd · Prepared by Gabriel &amp; Benson · March 2026 What Is Web App? Web App is a dashboard that automatically watches all 49 of your outlets on Grab and FoodPanda — from 6AM to 12AM daily. It tells you which stores are online, which menu items are unavailable, and sends an email alert the moment something goes wrong. No one needs to manually check anything. The Problem It Solves Before Web App, there was no way to know if a store quietly went offline on Grab or FoodPanda unless a customer complained. With 49 outlets across 2 platforms, that is 98 things to check every single hour — impossible to do manually. Menu items could be switched off for hours without anyone noticing, causing lost orders and customer complaints. Limitations — Full Breakdown The following is an honest, complete list of every known issue found in the system as of March 2026. These are documented so decisions can be made on what to fix, accept, or improve. 1. Timing &amp; Data Gaps 6-hour overnight blind spot: No monitoring runs between 12AM and 6AM SGT. Any store that goes offline during those hours will not be detected until 6AM the next morning. Platform status can be up to 1 hour out of date. Menu item availability can be up to 2 hours out of date. There is no real-time feed. If you manually trigger a sync at 9AM, the next automatic scrape for items will be skipped until 11AM (the system avoids double-running). This can silently delay data. 2. Scraper Fragility — Single Points of Failure Both scrapers log into the RestoSuite back-office website like a manager. If RestoSuite changes their website layout even slightly, the scraper breaks immediately and stops collecting data. If the RestoSuite login password is changed, scraping stops completely. The GitHub automation password must also be manually updated — it does not sync automatically. If RestoSuite’s website is down or slow, the scraper fails silently. There is no automatic retry — it simply waits for the next scheduled run. One outlet failing to scrape does not stop the rest, but a partial failure is still reported as a “success” — so gaps in data may not be immediately obvious. Scraper failure notifications do not exist yet. If the scraper stops running, nobody is alerted unless someone manually checks the Settings page. 3. Alerts &amp; Notifications Email only — no WhatsApp, SMS, or mobile push notifications. If the recipient does not check email promptly, alerts may be missed. If the email service (Resend) is temporarily down when an alert is triggered, that alert email is lost permanently. There is no retry or queue. If a store’s platform status flickers on/off rapidly (unstable connection), multiple alert emails can be sent in quick succession — no spam protection yet. If no recipient email is configured in Settings, alerts are silently not sent — no error is shown on screen. 4. Data Accuracy &amp; What It Actually Shows The system only shows what RestoSuite recorded. If a manager set the wrong status in RestoSuite , or if there is a sync delay between RestoSuite and Grab/ FoodPanda , the data shown may not match what customers actually see on the delivery apps. ONLINE in this system means the manager’s switch is ON in RestoSuite — not that customers can definitely order . Grab or FoodPanda can suspend a store on their own end for reasons we cannot see (e.g. operating hours, their own outage). If the database is empty or the scraper has not yet run, the dashboard shows 0 stores online — which looks like a total outage but is actually just no data yet. The two situations look identical. 5. System &amp; Cost Constraints GitHub Actions (the automation runner) has a monthly minute limit. The current usage is estimated at 1,000+ minutes/month. If usage grows, we may hit billing limits and scrapers will stop running until the next billing cycle. The web server (Render.com) runs on a single instance. If traffic spikes or a scraper run takes too long, the server can slow down or become temporarily unavailable. The database (Neon PostgreSQL) stores full HTML page snapshots from each scrape. This causes the database to grow over time and will need to be managed to avoid storage costs increasing. The system is currently set up to handle 49 outlets across 2 platforms. Some parts of the interface have this count written in directly — if the number of outlets changes significantly, those figures will need to be manually updated in the code. 6. Missing Features (Known Gaps) No WhatsApp or SMS alerts — currently email only. No push notifications to phone or desktop. No automatic retry if a scraper fails mid-run — next attempt is only on the next scheduled time. No overnight monitoring (12AM–6AM) — any incidents during those hours go undetected until morning. Cannot see what customers actually see on Grab or FoodPanda apps in real-time. Cannot monitor any platform other than Grab and FoodPanda — adding a new platform requires code changes. No in-app notification bell — alerts only go to email, not shown inside the dashboard itself. Reports and history are read-only — no ability to add manual notes or mark incidents as resolved with comments. 7. Security &amp; Access Notes Admin login credentials are stored in the server environment. If those credentials are changed on the RestoSuite side, the app must be redeployed to pick up the new values. Scraper login credentials ( RestoSuite email and password) are stored as GitHub secrets. If the RestoSuite password changes, someone must manually update the GitHub secret or scraping stops. The system has no brute-force protection on the login page — repeated wrong password attempts are not blocked. User sessions expire after 2 hours of inactivity. If a dashboard is left open for longer than 2 hours without interaction, the user is silently logged out. How It Gets Its Data Web App reads data from the RestoSuite back-office website — the same system your operations team already uses. A scheduled program logs in automatically, reads all the store and menu information, and saves it to the dashboard. This runs every 1 hour for store status and every 2 hours for menu items. Note: RestoSuite’s own API (developer connection) does not include the ability to check if a store is ON or OFF on Grab or FoodPanda . We checked all 59 available options.
